# 抓放任务：抓取条件、完整流程与结果判断

本文行数：215行，预期阅读时长：11分钟

**一次抓放要同时满足几何可达、运动可执行、接触能承载，以及释放后物体处于期望状态。MTC 的完整任务解连接了规划阶段，但物体是否抓牢、是否滑落、是否放稳，还需要独立判断。**

用现有桌面案例串起抓取位姿、接近、闭合、抬升、搬运与释放，解释物理条件和失败结果。MTC 机制见[第五章](../05_mtc_stages/README.md)，场景中允许碰撞与附着的含义见[第四章](../04_planning_scene/README.md)。

## 速记要点

- 物体位姿不是手爪目标；抓取还需要工具与物体的相对位姿、接近方向、开口和接触位置。
- 手爪 `close` 是运动目标，`attach` 是场景关系，二者都不能单独证明夹持成功。
- 抬升既要留出几何间隙，也会增加承载要求；静止时不滑不代表加速搬运时不滑。
- 放置目标通常描述物体应在哪里，不能把它不经转换就当成手爪原点的目标。
- 任务阶段日志可能在构建阶段就打印；看到 “lift” 或 “release” 不等于真实动作已经发生。
- 成功判据要覆盖物体最终位置、姿态或稳定性以及过程约束；控制器返回成功只覆盖其中一层。

本页默认讨论固定基座机械臂、平行双指夹爪和刚性物体。摩擦与稳定性的数值例子是简化模型推导，不是 Panda 的夹持能力或硬件设定建议。

## 2. 一个抓取目标需要哪些信息？

| 信息 | 为什么需要 |
| --- | --- |
| 物体位姿与时间 | 确定对象在哪，是否仍是测量时的位置 |
| 物体形状、尺寸和估计误差 | 判断手爪能否包围、手指能否接近、是否需要余量 |
| 抓取相对位姿 | 决定夹在哪里、工具朝向如何 |
| 工具坐标与夹爪几何 | 把抓取中心转换成实际规划 link 目标 |
| 接近方向与距离 | 为最终接触建立无碰撞通道 |
| 夹持与负载条件 | 判断接触力、摩擦和力矩是否足够 |
| 放置区域与姿态要求 | 明确搬运终点和成功判据 |

设世界为 `W`，物体为 `O`，抓取工具坐标为 `G`，变换 `⁽ᴬ⁾T_B` 将 B 系坐标转换到 A 系。若选定相对抓取变换 `⁽ᴼ⁾T_G`，则：

```text
⁽ᵂ⁾T_G = ⁽ᵂ⁾T_O · ⁽ᴼ⁾T_G
```

前者可以来自感知，后者来自物体几何与抓取策略。若 IK 使用手爪 link 而非 G，还要补上第二章解释的工具偏移。

预抓取位姿位于实际抓取位姿之前。对固定朝向的直线接近，若世界系单位接近方向为 `d_W`，接近距离为 `l`，可写成 `p_pre = p_grasp − l·d_W`。这里 `p` 与 `l` 单位为 m，方向向量无量纲。

本地桌面代码沿 `panda_hand` 的 `+Z` 接近 `0.08～0.14 m`，沿 `world` 的 `+Z` 抬升 `0.08～0.15 m`，释放后沿手爪 `−Z` 撤离 `0.01～0.12 m`。这些是源码请求范围，不是实测动作距离。

## 3. 例子一：盒子是否真的放在桌面上？

桌面案例中，以下位置都在 `world` 坐标系下，姿态为单位旋转，尺寸与位置单位均为 m：

| 对象 | 尺寸 `(X,Y,Z)` | 中心位置 |
| --- | --- | --- |
| 桌子 `table` | `(0.8,0.5,0.04)` | `(0.6,0,0.20)` |
| 盒子 `box` | `(0.04,0.04,0.08)` | `(0.6,−0.20,0.26)` |

**静态推导：**

```text
桌面高度 = 0.20 + 0.04/2 = 0.22 m
盒子底面 = 0.26 − 0.08/2 = 0.22 m
桌面 XY 范围 = [0.20,1.00] × [−0.25,0.25] m
盒子 XY 范围 = [0.58,0.62] × [−0.22,−0.18] m
```

几何上，盒子底面与桌面高度一致，水平投影在桌面范围内，靠近负 Y 桌沿的一侧还有 `0.03 m` 间隙。这解释了代码为何选 `z=0.26 m`；若误把物体中心设为桌面高度 `0.22 m`，盒子会有一半高度进入桌子。

**结论边界：** 面恰好接触是否被碰撞引擎判为相交还取决于数值误差和几何实现；上述计算也没有证明动力学接触稳定。桌面代码为盒子与桌子设置了阶段性的允许碰撞，适用范围见第四章。

## 4. 从预抓取到撤离，各阶段改变什么？

| 阶段 | 机器人动作或规划关系 | 判断该阶段成立的依据 |
| --- | --- | --- |
| 张开与预抓取 | 手爪开口足够，手臂到接近起点 | 有可达构型、接近通道与必要余量 |
| 接近 | 沿规定方向进入抓取位姿 | 手指对准目标，避免碰撞其他物体 |
| 允许预期接触 | 只调整指定碰撞对 | 豁免范围与接触意图一致 |
| 闭合 | 夹爪向闭合目标运动 | 实际接触、开口或力等反馈支持夹持判断 |
| 附着 | 在规划场景中记录手物相对关系 | 关系与实际抓取状态一致 |
| 抬升 | 物体离开支撑面 | 物体确实随手移动且未滑落 |
| 搬运 | 携带物体到放置构型 | 携物几何可通过，接触能承受运动负载 |
| 放置与打开 | 物体到达支撑位置，解除夹持 | 放置位姿及支撑条件满足要求 |
| 分离与撤离 | 恢复世界物体表示，手爪退出 | 物体保持在目标区域，手爪不再拖动物体 |

这是任务语义顺序，不表示所有测量与判断已在代码里实现。桌面源码在放置阶段的具体顺序是“打开手爪 → 恢复手物碰撞检查 → 分离 → 恢复盒桌碰撞检查 → 撤离”，应结合每个中间状态检查，而不是把这些场景操作任意交换。

本例没有单独的“到目标上方再向下放置”阶段；放置候选与前面的 `Connect` 负责构造相应连接。不能因为任务叫 pick-and-place，就假定源码已经包含独立下降、力控接触或柔顺放置。

## 5. 例子二：夹爪闭合为什么仍可能滑落？

库仑摩擦的简化静止条件为：

```text
||f_t|| ≤ μ f_n，且 f_n ≥ 0
```

`f_n` 是单个接触的法向压紧力，`f_t` 是切向摩擦力，单位 N；摩擦系数 `μ` 无量纲。摩擦力不是始终等于 `μ f_n`，该值表示这个模型中的可用上限。接触法向、摩擦锥及其近似条件见 [Modern Robotics：Friction](https://modernrobotics.northwestern.edu/nu-gm-book-resource/12-2-1-friction/)。

**输入（教学示意）：** 双指从左右对称夹持物体，两个接触面竖直，每侧法向力均为 `N`；物体质量 `m=0.5 kg`，`μ=0.5`，`g=9.81 m/s²`。假设没有转动、偏心力矩和其他外力，竖直方向仅靠两侧摩擦承重。

静止不下滑的必要承载条件为：

```text
2 μ N ≥ mg
N ≥ mg/(2μ) = 4.905 N（每侧）
```

若以竖直向上加速度 `a=2 m/s²` 抬升，则需要：

```text
2 μ N ≥ m(g+a)
N ≥ m(g+a)/(2μ) = 5.905 N（每侧）
```

**结果与解释：** 在此模型中，每侧 `5 N` 时，静止承重勉强满足条件，但上述加速抬升不满足。因此“刚夹住时没掉”不能证明搬运时也不会掉。

这些是简化的力平衡边界，没有安全余量；真实物体还可能有偏心、接触位置误差、表面变化、形变或夹爪传动限制。`N` 是接触法向力，不能直接当作某个驱动器的电流或任意 `GripperCommand` 参数。局部摩擦条件成立也不证明能抵抗所有方向的外部力矩。

本地的 `close` 命名目标和 `attachObject()` 没有提供上述接触测量。MoveIt 场景会按刚性附着关系移动物体模型，即使真实物体已经滑落，规划中的模型仍可能继续跟随手爪。

## 6. 例子三：代码的放置目标与 `target_area` 一致吗？

桌面源码定义了一个 `target_area`：中心 `(0.60,0.20,0.2225) m`，XY 尺寸 `0.12×0.12 m`；但没有把它加入碰撞对象列表。实际 `GeneratePlacePose` 的目标在 `world` 下是盒子位姿：

```text
位置 = (0.45, 0.20, 0.26) m
姿态 = 单位旋转
```

**静态结果：** 实际放置目标在 X 方向比区域中心小 `0.15 m`。如果任务意图是把盒子放入上述 `target_area` 的水平区域，这两处配置不一致。

按轴对齐的盒子完全落入区域的要求，区域 XY 边界先减去盒子半宽：

```text
区域边界：X ∈ [0.54,0.66]，Y ∈ [0.14,0.26] m
盒子中心允许范围：X ∈ [0.56,0.64]，Y ∈ [0.16,0.24] m
实际目标中心：(0.45,0.20) m → X 不满足
```

实际目标仍在桌面投影内，盒子底面也仍是 `0.22 m`，所以“放在桌上”与“放在指定区域里”是不同判据。

放置时还要考虑支撑稳定性。在水平平面、准静态、无其他外力的简化条件下，质心竖直投影位于支撑区域内部是避免倾覆的重要条件；释放速度、残余振动和倾斜接触会改变结果。仅让模型中心达到某点不能证明释放后能保持稳定。

## 7. 如果把硬编码物体位姿替换成感知结果

现有示例的对象位姿直接写在源码中。接入相机后，至少需要保留以下关系：

```text
相机测量的对象位姿与时间
    → 按对应时刻变换到规划参考系
    → 更新对象几何与位姿
    → 生成相对对象的抓取候选
    → 规划、执行并观察物体结果
```

不能只替换三个位置数字而继续沿用错误朝向、旧时间或不同物体 ID。位置误差会影响夹爪是否包住物体，朝向误差会影响接触面和接近通道；增大碰撞余量可以保守处理部分几何误差，但不会自动修复标定偏差或错误抓取姿态。

例如一个宽 `0.04 m` 的轴对齐物体，在理想总开口 `0.07 m` 下居中时每侧几何余量为 `(0.07−0.04)/2=0.015 m`。这只是简化开口关系：实际余量还要扣除定位误差、手指形状和接近要求，且本地单指 `open=0.035 m` 是否对应总开口 `0.07 m` 仍取决于模型，见第二章。

感知相关细节可查[位姿变换](../../perception/02_pose_transforms/README.md)、[误差传播](../../perception/04_uncertainty_propagation/README.md)和[时间对齐](../../perception/06_time_alignment/README.md)。

## 8. 成功、失败和恢复应该怎样描述？

任务成功可以定义为：机器人完成允许的动作，物体被释放到目标区域，并在规定观察时段内保持要求的姿态与位置，过程中没有禁止碰撞。区域、容差和观察时长应由具体任务给定，不能用一个通用阈值代替所有应用。

| 层次 | 可记录的证据 | 不能替代的证据 |
| --- | --- | --- |
| 规划成功 | 完整 MTC 解、阶段状态与代价 | 实际运动 |
| 执行成功 | 执行返回码和控制器结果 | 实际夹持 |
| 抓取成功 | 开口 / 力 / 视觉等证据共同支持物体随手移动 | 规划场景中的附着动画 |
| 放置成功 | 释放后物体在区域内，并满足稳定性要求 | 单次末端到达或任务函数返回 |

**统计示意：** 若预先定义的 20 次任务中有 16 次满足完整成功判据，另有规划失败、执行失败、抓空、释放后滑出区域各 1 次，那么任务成功率为 `16/20=80%`。不能删除失败样本后报告 `16/16=100%`。这里没有真实试验数据，20 也不是要求读者必做的次数；实际记录还要说明初始场景、模型配置、时间范围和判据。

| 失败类型 | 首先确认的事实 | 恢复方向 |
| --- | --- | --- |
| 规划无解 | 起点、对象位姿、约束和候选在哪层失败 | 修正信息或更换可行抓取候选 |
| 抓空 | 物体是否仍在原处，手爪是否真正接触 | 更新测量与场景，重建抓取请求 |
| 抬升后滑落 | 物体当前位置、夹持条件与运动负载 | 恢复真实物体表示，调整接触或运动策略 |
| 控制器中断 | 机器人实际停在哪、是否还在持物 | 根据当前状态重新建立任务起点 |
| 放置失败 | 支撑、目标区域、释放姿态与余速 | 修正放置条件与退出路径 |

恢复时不能无条件重跑旧任务：如果物体已被部分抬起或已经滑落，原来的世界位置与附着状态都可能过期。先确认当前事实，再决定从哪一阶段继续。

## 9. 源码中的结果证据到哪一层？

桌面程序检查 `init()`、`plan(5)` 和 `execute()`，末尾的 “Task execution succeeded” 对应执行返回码。它没有实现本章定义的目标区域检查、真实抓空检测、摩擦承载判断或释放后的稳定性测量。

此外，不少 `[W3][lift]`、`[W3][attach object]` 等日志在 `createTask()` 构建阶段时就打印；日志出现只证明程序构建到了该位置，不证明对应运动或接触已发生。应结合日志所在函数、执行结果和反馈判断。

分层示例把环境交给 `EnvironmentManager`，阶段构建交给 `TaskBuilder`，初始化、规划和执行交给 `RobotAppController`。这种组织便于维护，但功能范围仍按实际加入的 Stage 判断；目前不能把它当作已完成桌面抓放的替代实现。

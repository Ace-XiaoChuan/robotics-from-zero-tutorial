# 运动规划基础：路径、轨迹与执行

本文行数：228行，预期阅读时长：13分钟

解释构型空间、约束、采样规划与时间参数化，建立从目标到执行的整体认识。接口用法归第三章，轨迹与控制的系统推导归控制专题。

**运动规划回答“机械臂怎样合法地从当前构型到达目标”；时间参数化回答“什么时候到达沿途各点”；控制执行回答“实际有没有按要求走到”。** 三者的成功条件必须分开看。

## 速记要点

- **目标位姿不是整条运动。** 同一个末端位姿可能对应多个关节构型，逆运动学（IK）有解也不代表存在无碰撞的到达路径。
- **路径没有时间，轨迹有时间。** 同一条几何路径可以快走或慢走，但速度、加速度等限制会约束运动时间。
- **避障要看整台机器人。** 末端绕开障碍，不代表肘部、手爪或附着的物体都能通过。
- **关节插值与笛卡尔插值不同。** 关节角按比例变化，末端一般走曲线；末端沿直线走，关节变化一般不均匀。
- **终点约束与路径约束不同。** “到达时杯口朝上”和“全程杯口朝上”是两个规划问题。
- **规划、执行、任务完成分开判断。** 有轨迹、控制器报告成功、完整画圆或成功抓住物体，分别需要不同证据。

快速复习读上面六条及后面的三个例子即可。下文是概念说明、数学推导和仓库源码静态分析；没有把示意结果当作 Panda 实测结果。

## 1. 先分清输入和输出

| 对象 | 表达什么 | 本页记号或例子 |
| --- | --- | --- |
| 构型 configuration | 一组确定机器人姿态的关节变量 | 固定基座 Panda 手臂用七个转动关节，`q = [q1, …, q7]`，单位 rad |
| 末端位姿 pose | 工具相对某个参考坐标系的位置与姿态 | 位置 3 维，单位 m；姿态可用单位四元数表示，四元数分量无量纲 |
| 几何路径 path | 按顺序经过哪些构型 | `q(s)`，`s ∈ [0,1]` 是无量纲路径参数，不是秒 |
| 时间轨迹 trajectory | 何时处于哪个构型及相应运动速度 | `q(t)`，`t` 单位 s；转动关节速度 rad/s、加速度 rad/s² |
| 实际反馈 | 执行期间测到的关节运动 | `q_actual(t)`，需要与期望轨迹按时间、关节名称对齐 |

这里的 `q1…q7` 按 `panda_joint1…panda_joint7` 排列，不包含手指关节。读取实际轨迹时以消息里的 `joint_names` 为准，不能只凭数组长度猜关节顺序；移动关节的位置单位应为 m。

一个完整的规划请求至少需要：**机器人模型与规划组、有效起始状态、目标、规划场景、约束和规划时间预算**。位姿目标还要明确参考坐标系和目标 link；同一组位置数值放在相机坐标系和机器人基座坐标系下，含义完全不同。

```mermaid

flowchart LR
    A[模型、当前状态、场景与目标] --> B[搜索可行路径]
    B --> C[时间参数化与轨迹检查]
    C --> D[请求控制器执行]
    D --> E[反馈与任务结果判断]

```

这是概念分工，不要求程序恰好分成五个函数。常见 MoveIt 规划流水线会在一次规划调用内部完成路径搜索和时间参数化，因此 `plan()` 的返回对象可以已经带有时间信息。

## 2. 为什么 IK 有解，还需要规划？

### 构型空间：把整台机械臂看成一个点

工作空间描述末端或连杆在三维空间的位置；构型空间（configuration space，C-space）描述关节变量的组合。七关节手臂的一个构型就是七维空间中的一个点，不能仅用末端的三维位置替代。

设 `C_free` 为满足关节限位且无碰撞的构型集合，`G` 为满足目标容差的构型集合。几何规划要找到连续路径，使：

```text
q(0) = q_start
q(1) ∈ G
q(s) ∈ C_free，且满足路径约束，对所有 s ∈ [0,1] 成立
```

对于关节目标，`G` 是指定关节值附近的容差区域；对于位姿目标，`G` 可能包含多个 IK 分支。IK 只解决末端位姿与构型的对应，不能单独证明起点到该构型之间可通行。

### 例子一：起点、终点都合法，中间仍可能碰撞

**输入（二维构型空间教学示意）：** 两个转动关节，顺序为 `[q1,q2]`，单位 rad。起点 `A=(0,0)`，终点 `B=(1,1)`；假设碰撞区域是 `0.4 ≤ q1 ≤ 0.6` 且 `0.4 ≤ q2 ≤ 0.6`，其余相关区域没有障碍或限位问题。

- 直接插值 `q(s)=(s,s)`：在 `s=0.5` 处得到 `(0.5,0.5)`，落入碰撞区域。
- 绕行 `A → (0,0.8) → (1,0.8) → B`：三段分别位于 `q1=0`、`q2=0.8`、`q1=1`，均绕开该区域。

**结果与解释：** 起终点合法不能推出连接它们的直线合法。绕行路径几何上可行，但拐角怎样减速、是否平滑，仍是后续轨迹处理的问题。这是人为定义的构型障碍，不是 Panda 的真实碰撞图；真实构型障碍由所有连杆几何与环境共同决定。

### 采样规划器如何找路？

以 RRT-Connect 的思路为例：从起点和目标附近扩展两棵树，采样候选构型，尝试连接，并检查新增运动段是否合法，直到两棵树连通或预算耗尽。它不需要把整个高维空间铺成密集网格，但狭窄通道仍可能很难找到。

| 方法 | 复习时记住的特点 |
| --- | --- |
| RRT-Connect | 常用于尽快找到一条可行路径，不承诺最短路径 |
| PRM | 先构建可连通的路线图，适合在可复用场景中处理多次查询 |
| RRT* | 在相应理论条件下随采样增加渐近趋向最优；有限时间返回值不保证已最优 |

算法性质见 [OMPL 规划器说明](https://ompl.kavrakilab.org/planners.html)。这里用于解释采样思路，不表示仓库代码已明确选择或比较了这些规划器。

**超时表示“这次没找到”，不等于证明无解。** 增加搜索时间可能帮助找到狭窄通道，但不能修复错误坐标系、碰撞中的起点或不可达目标。路径短、障碍间隙大、关节变化小、执行时间短也是不同优化目标。

碰撞检查还涉及分辨率：只检查两个端点会漏掉中间的碰撞。MoveIt 的 OMPL 接口会对运动段离散检查；分辨率过粗可能漏检，过细会增加计算量。相关配置含义见 [Humble OMPL 接口文档](https://moveit.picknik.ai/humble/doc/examples/ompl_interface/ompl_interface_tutorial.html)。因此“无碰撞”始终依赖模型、场景和检查配置。

## 3. 到达目标，与沿指定形状运动

| 请求 | 固定了什么 | 中间怎样走 |
| --- | --- | --- |
| 关节目标 | 终点关节构型及容差 | 规划器搜索满足约束的连接路径 |
| 末端位姿目标 | 终点的位置、姿态及容差 | 可选择允许的 IK 解和绕行路线，不保证末端走直线 |
| 笛卡尔路点 | 末端依次经过的位姿 | 对指定段插值并求关节解；不是通用的自动绕障搜索 |
| 路径约束 | 整条路径须维持的条件 | 例如搬杯子时始终保持规定朝向，起点也必须满足约束 |

关节空间直线通常不会映射成末端直线，因为正运动学是非线性的。反过来，笛卡尔空间中很小的一步，在奇异位形附近也可能要求很大的关节变化，甚至找不到连续、合法的 IK 解。

普通位姿目标适合“能绕路，到那里就行”；画线、插入和沿表面移动则需要明确路径要求。若指定直线穿过障碍，合理结果可以是失败或只返回前面可行的部分，而不是自行改变所要求的形状。MoveIt 接口的目标、路径约束和路点示例见 [Humble C++ 教程](https://moveit.picknik.ai/humble/doc/examples/move_group_interface/move_group_interface_tutorial.html)。

## 4. 有路径以后，为什么还要安排时间？

将几何路径 `q(s)` 配上时间规律 `s(t)`，得到 `q(t)=q(s(t))`。对光滑段使用链式法则：

```text
q_dot(t)  = q'(s) · s_dot(t)
q_ddot(t) = q''(s) · s_dot(t)² + q'(s) · s_ddot(t)
```

撇号是对无量纲 `s` 求导，点号是对秒求导。时间参数化要让各关节的速度、加速度不超限；进一步还可以限制 jerk（加速度的变化率，转动关节单位 rad/s³）。

### 例子二：同一段关节运动，2 秒完成与 1 秒完成

**输入（单关节数学示意）：** 一个转动关节从 `0 rad` 到 `1 rad`，总时长为 `T`，令 `u=t/T ∈ [0,1]`，采用三次时间规律：

```text
q(t) = (1 rad) · (3u² − 2u³)
最大速度 = (1 rad) · 1.5/T
最大加速度绝对值 = (1 rad) · 6/T²
```

| 总时长 | 中点位置 | 最大速度 | 最大加速度绝对值 |
| --- | --- | --- | --- |
| `T=2 s` | `0.5 rad` | `0.75 rad/s` | `1.5 rad/s²` |
| `T=1 s` | `0.5 rad` | `1.5 rad/s` | `6 rad/s²` |

**结果与解释：** 假设限制为 `1 rad/s` 和 `2 rad/s²`，2 秒方案满足这两项限制，1 秒方案同时超限。运动时间减半，速度变为两倍、加速度变为四倍；几何路径本身没有变化。以上是解析推导，不是仓库规划器的输出。

这个三次曲线起终速度为零，但起终加速度不为零；与静止段直接拼接会有加速度跳变，不能据此宣称满足 jerk 限制。满足速度和加速度限制，也不等于已验证电机力矩、负载、摩擦和跟踪能力。

MoveIt 的时间参数化会根据关节限制生成时间、速度和加速度信息；具体后处理也可能在容差内改变几何路径，需要考虑再次检查碰撞。详见 [Humble 时间参数化说明](https://moveit.picknik.ai/humble/doc/examples/time_parameterization/time_parameterization_tutorial.html)。

仓库的 [joint_limits.yaml](../packages/panda_moveit_config/config/joint_limits.yaml) 写有默认速度、加速度缩放因子 `0.1`，但其中关节条目也写着 `has_acceleration_limits: false`。不能把这个文件解释成“所有关节已经有明确且验证过的加速度上限”，也不能把 `0.1` 当作末端恒速 `0.1 m/s`；最终生效值还取决于配置加载、请求和具体轨迹生成流程。

## 5. 例子三：仓库的“直线加圆”到底做了什么？

对应源码：[draw_line_and_circle.cpp](../packages/hello_moveit/src/draw_line_and_circle.cpp)。规划组是 `panda_arm`，起点取自 `getCurrentPose().pose`，后续只修改位置，保留起始四元数。

### 输入：路点的几何含义

为方便阅读，假设取得的末端起点在参考坐标系 `F` 下为 `(x0,y0,z0)`，并且路点解释所用的参考坐标系也是 `F`。源码取出 `.pose` 后丢弃了 `PoseStamped` 的 header，因此实际运行前仍需核对这两个坐标系一致；可视化使用 `panda_link0` 并不能单独证明路点也按它解释。

1. 沿 `F` 的 `+Y` 方向移动 `0.15 m`，得到直线终点 `L=(x0,y0+0.15,z0)`。
2. 圆心取 `C=(x0,y0+0.15,z0−0.05)`，半径 `r=0.05 m`，位于 `F` 的 Y-Z 平面。
3. 按 `θ=0,0.1,…,6.2 rad` 生成圆上路点，姿态不变：

```text
x = x0
y = y0 + 0.15 + 0.05 sin(θ)
z = z0 − 0.05 + 0.05 cos(θ)
```

源码使用 `θ <= 2π`、每次增加 `0.1 rad`，实际最后一次是约 `6.2 rad`，不是 `2π`。这些路点随后形成分段插值路径，不是直接提交一个解析圆。

### 结果与解释：圆并未严格闭合

由上述公式得到最后一个路点相对 `L` 的偏移：

```text
Δy = 0.05 sin(6.2)          ≈ −0.004154 m
Δz = 0.05 (cos(6.2) − 1)    ≈ −0.000173 m
首尾距离                    ≈ 0.004158 m = 4.16 mm
```

因此，即使路点全部算完，也不能说请求的几何路径已经严格闭合。若任务要求闭合，生成路点时应显式加入圆的起始点作为最后一点；这是改进建议，本页没有修改源码。

直线在 `L` 处沿 `+Y`，理想圆在 `θ=0` 处的切向也沿 `+Y`，所以理想几何的切向方向接得上。但圆弧有曲率、直线无曲率，且源码最终使用离散路点，不能仅凭“圆心放在下方”就声称速度、加速度都平滑。

### 路径完成比例与执行分支

源码中的关键逻辑为：

```cpp
const double jump_threshold = 0.0;
const double eef_step = 0.01;
double fraction = move_group_interface.computeCartesianPath(
    waypoints, eef_step, jump_threshold, trajectory);
if (fraction > 0.9) {
    // 原代码将 trajectory 放入 Plan 后调用 execute()
}
```

- `eef_step=0.01` 的平移步长单位为 m，用于笛卡尔路径离散计算，不是 `0.01 s` 的控制周期，也不是 `0.01 m/s` 的运行速度。
- 按本例使用的 Humble 接口语义，`jump_threshold=0.0` 禁用该项关节跳跃阈值检查，不表示“绝不允许跳跃”，也不等于关闭所有碰撞和有效性检查。
- `fraction` 表示请求路径算出的完成比例，不是多次试验的成功率，也不能不经核对就换算成相同比例的圆周长度。
- 若 `fraction=0.95`，源码仍会进入执行分支；若恰为 `0.9`，则不会。失败前的部分路径可以被提交执行，后面缺失的部分不会因调用 `execute()` 自动补齐。

这些参数的教程语义见 [Humble 笛卡尔路径示例](https://moveit.picknik.ai/humble/doc/examples/move_group_interface/move_group_interface_tutorial.html#cartesian-paths)；实际编译使用的重载和行为需与所安装 MoveIt 版本匹配。

**完整画圆至少要分别核对：** 路点是否闭合、路径是否完整生成、关节变化与轨迹时间是否合理、执行是否成功、反馈是否满足绘图误差要求。`fraction=1` 本身只覆盖其中一部分，也不能证明笔尖已经在实际表面画出所需图形。

## 6. 规划成功之后，还要看什么？

| 层次 | 应查看的证据 | 单独不足以证明什么 |
| --- | --- | --- |
| 规划 | 返回码、非空轨迹、终点与路径约束 | 控制器已经执行 |
| 执行请求 | 控制器可用、关节名称匹配、时间信息有效、当前状态与轨迹起点相符 | 实际运动一定符合要求 |
| 执行结果 | `execute()` 返回码、控制器结果、带时间的关节反馈 | 画圆闭合、抓取成功等任务结果 |
| 任务结果 | 末端误差、几何覆盖情况，或物体是否真的被抓住 | 其他场景下也会同样成功 |

[hello_moveit.cpp](../packages/hello_moveit/src/hello_moveit.cpp) 检查了 `plan()` 的返回值，但调用 `execute(plan)` 后没有检查其返回值；绘图示例同样没有检查执行返回值。因而源码能证明“满足分支条件后发起执行请求”，不能证明“实际执行成功”。

对转动关节，可定义跟踪误差 `e_i(t)=q_desired,i(t)−q_actual,i(t)`，单位 rad；两者必须使用相同关节顺序和时间基准，连续转动关节还要按周期处理角度差。任务空间的位置误差则用相同参考坐标系下的末端位置差，单位 m。规划轨迹在 RViz 中显示得正确，不是这些误差已经测量过的证据。

此外，规划使用的是某一时刻获得的状态与场景。等待用户点击执行期间，机器人或障碍物可能变化；旧轨迹不能自动代表新场景中的有效运动。这里说明执行前重新核对状态与场景的原因，不假定本例已实现动态避障。

## 7. 遇到问题时按层定位

| 现象 | 优先检查什么 | 为什么 |
| --- | --- | --- |
| 位姿目标找不到 IK | 参考系、目标 link、姿态、可达范围、关节限位 | 位置看似可达，完整姿态仍可能不可达 |
| 起点无效 | 当前关节状态、自碰撞、场景障碍和路径约束 | 规划起点本身也必须合法 |
| IK 有解但规划超时 | 连通路径、障碍间隙、约束和搜索预算 | 有合法终点不代表容易找到到达路径 |
| 笛卡尔 `fraction < 1` | 首个失败段的 IK、碰撞、限位、奇异性或跳跃 | 一味减小步长不能消除几何不可行性 |
| `fraction=1` 但关节变化很大 | IK 分支连续性、奇异位形、跳跃检查配置 | 末端路径连续不保证关节变化温和 |
| 规划成功却执行失败 | 控制器映射、轨迹关节名、时间戳、起点差异、返回码 | 规划接口与控制接口是不同环节 |
| 执行成功但绘图或抓取不符合要求 | 工具坐标、标定、跟踪误差、接触和任务判据 | 控制器的完成条件不等同于整个任务目标 |

# 05：数据记录与排错

本文行数：92行，预期阅读时长：4分钟

**先确认程序与连接，再核对数据语义和业务结果。记录消息能帮助解释发生了什么，但不能自动恢复完整机器人世界。**

## 速记：按层排查

| 层次 | 先问什么 | 一个典型问题 |
| --- | --- | --- |
| 环境与程序 | 启动的是预期版本吗？ | 新源码没构建，或终端加载了另一份安装环境 |
| 发现与连接 | 节点、名称、类型和 QoS 对得上吗？ | `/Navigation` 与 `/navigation` 不同 |
| 数据 | 数值的单位、坐标系、时刻正确吗？ | 收到旧位置，却当成当前状态 |
| 业务 | 有没有真正执行并满足完成条件？ | 有反馈，但没有运动指令或永远到不了目标 |

这几层可能同时有问题。修好连接，只能继续检查数据和业务，不能直接宣称整个任务完成。

## 例子 1：Action 服务端明明启动了，客户端却找不到

**输入：** 现有客户端使用 `Navigation`，服务端使用 `navigation`，均在默认命名空间且没有重映射。

**结果（源码推导）：** 两个完整名称分别为 `/Navigation` 和 `/navigation`。客户端等待的那个服务端不存在，单纯增加等待时间无法修正名称。

名字改对后仍有第二个问题：目标是 `(5, 3) m`，模拟位置始终在 `y=0`，最小距离为 `3 m`，不能达到 `0.1 m` 内。这个推导见[第一章](../01_nodes_interfaces/README.md)。

## 例子 2：频率正常，位置为何已经旧了

**教学输入：** `/robot_pose` 在观察终端约每秒输出一条消息，但某条消息的采样时间为 `10.0 s`，消费时同一时钟已到 `12.0 s`。

**结果：** 这条数据年龄为 `2.0 s`；“约 1 Hz 收到消息”并不能证明它足够新。频率与延迟是两个不同指标。

可能原因包括生产者使用了旧测量、缓存积压或回调处理过慢。应分别看时间戳、生产者逻辑和执行情况。命令行工具本身也是订阅者，其观察结果还受 QoS 和机器负载影响。

## 例子 3：怎样留下一份有解释价值的记录

**教学条件：** Lesson 1 已满足依赖并正常启动。以下命令仅供需要时参考，本次未执行录制：

```bash
ros2 bag record -o status_sample /battery_level /robot_pose
```

输出目录 `status_sample` 应尚未存在；结束录制后查看：

```bash
ros2 bag info status_sample
```

**预期结果：** 工具列出实际录入的话题、类型、消息数量和录制时间范围。话题名出现在录制命令里，不保证对应发布者存在或已录到消息。

例如假设电量有 10 条、位置只有 1 条，至少说明不能将它们按“第 n 条对第 n 条”简单配对；要结合时间和实际数据来源判断是否满足需要。

| 想回看什么 | 需要保存或另外记录什么 |
| --- | --- |
| 电量与位置随时间的变化 | 两个状态话题及字段、单位说明 |
| 相机中的目标如何转到基座 | 相关测量、TF、静态外参及时间约定 |
| 导航任务为何结束 | 目标、反馈、结果与必要日志；仅两条状态话题不够 |
| 仿真里重新执行相同动作 | 初始状态、模型、控制配置、动作和时间；bag 本身不包含所有这些内容 |

因此 `rosbag2` 适合记录消息流；机器人 episode 还需要定义观测与动作的配对、重置和执行含义，这部分放在后续数据采集主题。[Humble rosbag2 教程](https://raw.githubusercontent.com/ros2/ros2_documentation/humble/source/Tutorials/Beginner-CLI-Tools/Recording-And-Playing-Back-Data/Recording-And-Playing-Back-Data.rst)

## 例子 4：回放究竟恢复了什么

在独立测试环境中，已有记录可用下面的命令重新发布：

```bash
ros2 bag play status_sample
```

**预期结果：** 回放工具按记录安排发送消息；原来的传感器、状态节点和机器人动力学并没有因此重新运行。若真实发布者也在发同一话题，接收端还可能混合两路数据。

记录中的消息时间戳与当前系统时间可能相隔很久。需要按记录时间回放的消费者，应协调仿真时钟；例如播放器使用 `--clock` 发布回放时钟，消费者启用 `use_sim_time`。这不会自动补齐缺失 TF，也不应与另一 `/clock` 来源冲突。参照 [Humble rosbag2 回放选项](https://raw.githubusercontent.com/ros2/rosbag2/humble/README.md)。

## 按问题查命令

下面的 `<包名>` 等表示待替换项，不需要背命令。

| 想知道什么 | 工具 | 结果怎样读 |
| --- | --- | --- |
| 当前环境找到哪份包 | `ros2 pkg prefix <包名>` | 安装路径不同，可能运行的不是刚改的源码 |
| 节点有哪些连接 | `ros2 node info <节点名>` | 看它实际发布、订阅或提供的名称 |
| 话题两端是否匹配 | `ros2 topic info -v <话题名>` | 看端点、类型和 QoS |
| 消息实际内容 | `ros2 topic echo <话题名>` | 核对字段、坐标系和时间，而不仅是“有输出” |
| 观察端收到的频率 | `ros2 topic hz <话题名>` | 接收频率估计，不是硬实时证明 |
| Action 是否有对应服务端 | `ros2 action info <名称>` | 再结合客户端日志判断是否接受与结束 |

若两个终端连节点都互相发现不了，再核对 `ROS_DOMAIN_ID`、网络发现设置和加载环境；同域只是正常发现的前提之一，不是通信成功的充分条件。

详细案例问题集中在 [Lesson 1 问题记录](../examples/communication/ros2_interfaces_notes.md#issues)。求助时给出启动目录、完整命令、实际日志、预期结果及相关数据，不必把所有工具输出都堆进去。

本章的消息数量、时间和输出是教学示意；未录制 bag、回放数据或重新验证整个 ROS 系统。

# S0 · 单元 05：调试与错误定位

本文行数：76行，预期阅读时长：4分钟

**一句话回忆：先把“预期、实际、最小复现和第一处错误”写清楚，再选择日志、断点或追踪工具；不要从最后一行连锁报错猜起因。**

## 速记

- 先记录启动目录、完整命令、输入文件、环境和预期结果；同一错误没有这些上下文往往无法复现。
- 区分配置错误、编译错误、启动错误、运行时错误和结果错误。它们的检查入口不同。
- 日志要包含时间、级别、节点/线程和关键输入摘要；不要只打印“失败了”。
- 回溯（stack trace）从触发异常的位置向上看调用链；第一处属于自己代码的异常通常比最后一行更有价值。
- 调试器用于回答“哪一行、哪些变量、怎样走到这里”；日志用于回答“程序在真实运行中经过了什么状态”。
- 修复后重跑原始复现用例，并确认没有把错误掩盖成静默默认值。

## 例子：从完整错误中找第一处问题

**条件 / 输入：** 一个节点启动时打印：

```text
[ERROR] [planner]: parameter 'max_velocity' must be > 0, got -1.0
[ERROR] [planner]: failed to configure controller
[ERROR] [launch]: process exited with code 1
```

**结果：** 首先检查 `max_velocity` 的来源和单位，而不是去修改 launch 的退出处理。后两行是前一错误导致的连锁结果。

**解释：** `-1.0` 已经给出了可验证的边界违例。应核对 YAML 键名、参数覆盖顺序和速度单位（例如 rad/s），再决定是修正配置还是修正校验逻辑。

结果依据：日志为教学示意，展示定位顺序，不代表某次真实运行。

## 例子：用最小输入隔离数值问题

假设轨迹跟踪出现末端抖动，先把问题缩小成一个可打印的误差计算：

```python
import numpy as np

target = np.array([0.10, 0.00, 0.20])  # m，基座坐标系
actual = np.array([0.11, 0.00, 0.20])  # m，同一坐标系
error = target - actual
print("error(m)=", error, "norm(m)=", np.linalg.norm(error))
```

**结果：** `error(m)` 为 `[-0.01, 0.00, 0.00]`，范数为 `0.01 m`。若完整控制程序报告相反方向，优先检查误差定义、坐标系和数据时间戳。

**解释：** 最小例子去掉了控制器、线程和仿真器的干扰，只验证一个假设。它不能证明控制器稳定，却能排除“减法方向或单位错误”这一类问题。

## 工具怎样分工

| 工具 | 适合回答的问题 | 先保留什么证据 |
| --- | --- | --- |
| 日志与 `ros2 node list` | 节点是否启动、参数和状态怎样变化 | 完整命令、时间戳、关键参数 |
| 编译器警告 | 类型、未使用变量、接口不一致 | 首个 warning/error 及源码位置 |
| `gdb` / IDE 断点 | 哪一行访问了错误数据、调用链是什么 | backtrace、变量值、触发输入 |
| `print()` / `ros2 topic echo` | 消息内容、数组形状和单位是否正确 | 一小段带时间的输入输出 |
| 录制数据或固定随机种子 | 间歇性错误能否重放 | 数据文件、种子、版本和配置 |

## 遇到问题时查

| 现象 | 原因或检查方向 |
| --- | --- |
| 程序立即退出 | 看退出码和第一处启动错误；确认参数文件、库路径和工作区是否已 source |
| 只有“结果不对”没有报错 | 固定输入，打印形状、单位、坐标系、时间戳和中间量 |
| 偶尔失败 | 保存随机种子、输入数据和线程/时间信息；先增加状态日志再改算法 |
| 日志很多但找不到重点 | 提高关键路径级别，给日志加组件名和阶段名；从第一条 ERROR 向前看 |
| 加了默认值后不再报错但行为异常 | 检查默认值是否掩盖缺失配置；对必须参数使用显式校验 |
| 修复后仍像旧代码 | 清理或重新构建对应 target，确认实际运行的可执行文件和安装空间 |
